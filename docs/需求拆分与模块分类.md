# 电商智能系统（ecom）· 需求拆分与模块分类

> 项目代号：ecom ｜ 课程：Web 应用项目实训（CW3104）
> 依据：《电商智能系统_ClaudeCode落地提示词.md》 ｜ 版本：v1.0（2026-09-15）

## 一、项目定位

面向店铺运营的电商系统，定位采用「**店铺自用 + 消费者前台**」完整电商形态（对应提示词手册「避坑提醒 1：方案 A」）：

- **运营后台**：店铺运营人员使用，管理商品、订单、营销、数据。
- **消费者前台**：C 端用户注册、浏览、加购、下单、支付、收货、评价。

核心卖点：用**规则引擎**替代重复性人工决策（智能补货建议、库存预警、智能客服、个性化推荐），全部可解释、可配置、无训练成本。

## 二、角色定义（5 个）

| 角色 key | 名称 | 权限范围 |
|---|---|---|
| `super_admin` | 超级管理员 | 全部功能，含用户/角色/菜单管理 |
| `product_op` | 商品运营 | 类目、商品、SKU、库存预警、销量预测、商品相关数据 |
| `market_op` | 活动运营 | 优惠券管理、营销数据看板 |
| `cs_op` | 客服主管 | 知识库维护、会话记录、评价管理 |
| `member` | 消费者 | 前台注册自动获得：浏览、搜索、购物车、下单支付、订单售后、评价、客服咨询 |

说明：消费者与运营人员共用一套登录/JWT/权限体系（`sys_user.user_type` 区分：0=运营，1=消费者），登录后按角色动态渲染菜单。

## 三、模块拆分

共 **1 个工程基础 + 8 个业务模块 + 1 个预留模块 + 1 个收尾阶段**，与 P0-P8 阶段一一对应。

| # | 模块 | 核心功能 | 关键规则/验收点 | 阶段 | 主要角色 |
|---|------|---------|----------------|------|---------|
| 0 | 工程基础 | 多模块 Maven、基础件（ResponseResult/异常/跨域/分页）、前后端连通、数据库脚本 | `mvn clean install` 全绿；`/health` 前后端打通 | P0 | — |
| 1 | 鉴权与权限管理 | 登录/退出、JWT、RBAC、动态菜单路由、按钮级权限、操作日志 | 不登录访问受保护接口返回 401；无权限菜单不显示 | P1 | 全部 |
| 2 | 商品管理 | 多级类目树（不限层级）、SPU/SKU 与规格笛卡尔积、MinIO 图床、上下架、前台商品详情 | 类目层级不限（原三级限制已按用户要求取消）；增删规格维度不丢已填价格库存；库存为 0 自动下架 | P2 | 商品运营 |
| 3 | 购物车与交易 | 购物车、地址簿、下单（锁库存/幂等/优惠券核销）、模拟支付与回调、优惠券管理 | 快速双击只生成一笔订单；回调重复调用库存只扣一次；15 分钟未支付自动取消并释放库存 | P3 | 消费者 / 活动运营 |
| 4 | 订单与售后 | 订单状态机、物流轨迹模拟、退款审核、后台订单管理 | 非法状态流转被拒绝；退款后状态与库存正确变化 | P4 | 消费者 / 运营 |
| 5 | 智能供应链 | 库存预警（6h 定时扫描）、销量预测（加权移动平均，每日 2:00） | 同一 SKU 连续触发只推首次；新 SKU 无历史数据有兜底值；阈值可配置 | P5 | 商品运营 |
| 6 | 数据看板 | 实时指标、销售趋势、商品排行、类目占比、订单漏斗 | GMV 以支付成功为准；T+1 预计算；同比无数据显示 "-"；按角色控制数据范围 | P6 | 商品/活动运营 |
| 7 | 智能客服与搜索 | 知识库匹配客服（置信度 ≥85% 自动回复，否则转人工）、同义词/拼音搜索、热门搜索 | 答不上来的问题进「待补充」列表；无结果时推荐相近类目商品 | P7 | 消费者 / 客服主管 |
| 8 | 运营数据支撑（预留） | 商品评价、用户行为采集（埋点） | 行为表支撑 P6 漏斗与推荐；评价支撑 P8 演示流程 | 后期简化实现 | 消费者 |
| 9 | 收尾 | 演示数据、部署（Nginx）、README、Swagger 导出、功能边界清单 | 全新环境按 README 能跑起来 | P8 | — |

### 依赖关系

```
P0（骨架）→ P1（鉴权，全部模块的地基）→ P2（商品）→ P3（交易闭环）
                                              ↓
                              P4（订单售后）→ P5 / P6 / P7（相互独立，可并行）
                                              ↓
                                          P8（收尾）
```

- **主干**：P0-P4 是硬骨头（约 70% 工作量），交易闭环不通后面全白搭。
- **附加项**：P5-P7 智能模块彼此独立，进度落后时 P7 可延后，不影响主流程演示。
- **数据依赖**：P5 预测需要 P3 的订单销量；P6 看板需要 P3/P4 的订单与行为数据；推荐需要行为表。

## 四、需求缺口与处理决策（开工前已确认）

对照提示词手册拆分时发现 5 处缺口，处理决策如下：

| # | 缺口 | 决策 |
|---|------|------|
| 1 | 「个性化推荐」只在背景卖点与答辩话术中出现，无对应实施阶段 | **完整预留、简化实现**：不单独建推荐模块，用 `ec_user_behavior` 行为数据 + 类目匹配在商品详情/首页做简化推荐 |
| 2 | 「商品评价」出现在 P8 演示流程，无对应实施阶段 | **完整预留、简化实现**：建 `ec_review` 表，随 P7 后补一个简单评价功能（下单完成后可评） |
| 3 | `ec_address`（收货地址簿）未在 P3 表清单中，但 orderConfirm「地址+商品+优惠券选择」必须要有地址簿 | 补入 P3：地址增删改查 + 默认地址 |
| 4 | `ec_refund`（退款单）未在 P4 表清单中，但「管理员审核退款」需要记录退款原因/金额/审核状态 | 补入 P4：退款单 + 审核流 |
| 5 | 优惠券管理界面、前台商品详情页 `productDetail.vue` 无归属阶段 | 优惠券管理（活动运营）随 P3 做；商品详情页随 P2/P3 做 |

## 五、智能功能实现边界（答辩说明用）

| 功能 | 实现方式 | 边界 |
|------|---------|------|
| 销量预测 | 加权移动平均（近 7 天 0.5 / 8-30 天 0.3 / 31-90 天 0.2）× 促销系数 × 季节系数 | 无突发事件的稳定品类较准；新品用同类目均值兜底；仅作建议展示，不自动补货 |
| 库存预警 | 定时扫描 + 阈值比较（阈值走 `ec_sys_config`） | 只做缺货/积压两类，不做安全库存的动态计算 |
| 智能客服 | 分词 + 编辑距离/余弦相似度，置信度 ≥85% 自动回复 | 知识库覆盖的问题准确率高；未命中转人工并进入待补充列表 |
| 个性化推荐 | 行为权重 + 类目匹配 | 规则版推荐，无协同过滤；冷启动用热销兜底 |

> 统一话术：本系统的智能定位是「**规则引擎驱动的业务自动化**」，不是机器学习——完全可解释、可配置、无训练成本。
