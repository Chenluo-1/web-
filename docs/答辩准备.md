# 电商智能系统 · 答辩准备

> 一句话定位：**一套「店铺运营中台 + 消费者商城」的电商闭环系统**——RBAC 双层鉴权、下单到售后的交易闭环、T+1 数据看板、以及三个规则型智能模块（补货预警 / 销量预测 / 客服应答）。

---

## 一、3 分钟讲解主线（照着讲，别背代码）

1. **做什么**：消费者能逛、加购、下单、支付、评价；运营能管商品、发货、退款、看数据、管客服知识库。
2. **怎么分层**：前端 Vue3（菜单驱动动态路由）→ 8082 代理 → Spring Boot 8888 → MySQL / Redis / MinIO。
3. **最难的三件事**（这也是答辩的得分点）：
   - **谁能进来**：JWT + Redis 登录态 + 路径级/方法级双层授权；
   - **钱不能算错**：下单幂等 + 条件更新扣库存 + 订单状态机 + 超时自动回补；
   - **数据要能看**：6 万订单实时聚合扛不住，改 T+1 汇总表 + 5 分钟缓存。
4. **智能化不是调大模型**：客服是 2-gram 相似度命中知识库，预测是加权移动平均，预警是阈值 + 规则——**可解释、可配置、不花钱**。
5. **结果**：200 商品 / 687 SKU / 1206 用户 / 6.3 万订单 / 13 万行为埋点，全链路可点通。

**演示动线（5 分钟）**：登录（切 3 个角色看菜单差异）→ 商城加购下单支付 → 后台发货 → 看板指标 → 客服问答 → 库存预警。

## 二、架构一句话版

```
Vue3(8082) ──/api 代理──▶ Spring Boot(8888)
                            ├─ Filter: JWT → Redis 取登录态 → SecurityContext
                            ├─ 授权: 路径表(CustomAuthorizationManager) + @PreAuthorize
                            ├─ Controller → Service(接口) → Impl → Mapper → MySQL
                            ├─ AOP: @OperLog 写 sys_oper_log
                            └─ Task: 超时取消 / 日报汇总 / 库存预警
                        MySQL 3306 · Redis 6379（登录态+看板缓存）· MinIO 9000（商品图）
```

后端两个模块**同包名 cn.ecom**：`ecom-system` 只放 controller/filter/config，业务全在 `ecom-common`（service/impl/mapper/task）。这是这套骨架的约定，也是被问到时可以承认的"分层不彻底"。

## 三、五个技术亮点（每个都能展开讲 1 分钟）

### 1. 双层鉴权（安全实验的核心）
- **路径级**：`CustomAuthorizationManager` 维护「方法+路径 → 权限标识」表（18 条），白名单外一律过它。
- **方法级**：`@PreAuthorize("@ss.hasPermission('product:add')")`。
- **为什么两层**：只靠注解，漏加一个就是越权洞；只靠路径，细粒度操作（如"上下架"）表达不了。两层共用同一个 `PermissionService`，规则只有一份。
- **token 为什么要存 Redis**：能强制下线、禁用账号立即生效、权限变更不必等 token 过期；过滤器里比对 `token.equals(loginUser.getToken())` 才算登录态有效。
- **坑（可以主动说，显专业）**：白名单里不能放带 `@PreAuthorize` 的接口，否则未登录会从 401 变 403。

### 2. 下单一致性（最容易被追问）
- **幂等**：`UNIQUE KEY uk_user_idem (user_id, idempotency_key)`，前端每次下单带一个 key，重复提交直接被唯一索引挡掉。
- **防超卖**：`UPDATE ec_sku SET stock = stock - ? WHERE id = ? AND stock >= ?`，**判断和扣减在同一条 SQL 里**，影响行数为 0 就抛异常；绝不做"先查库存再减"。
- **回补**：取消/退款时逐单独立事务（`REQUIRES_NEW`），保证"订单取消"和"库存/券回补"同生共死，不会出现订单取消了库存没还。
- **兜底**：`OrderTimeoutTask` 每分钟扫 `expire_time` 已过期的待支付单，取消 + 回补。

### 3. 订单状态机
```
0 待支付 → 1 待发货 / 4 已取消
1 待发货 → 2 运输中 / 5 退款中
2 运输中 → 3 已完成
5 退款中 → 6 已退款 / 1 驳回
3、4、6 为终态
```
用 `LEGAL_TRANSITIONS` 表校验，非法流转一律抛 `ORDER_STATUS_ERROR`——避免"已取消的单又被发货"这种脏状态。

### 4. 数据看板：为什么不是"实时算"
- 6.3 万订单、760 天，全量聚合一次要 **5 分钟**，页面上不可能这么查。
- 方案：**T+1 汇总表**（`ec_stat_daily` / `ec_product_sales_daily`）+ 每日 1:30 定时任务 + 手动重算接口 `POST /dashboard/aggregate?days=760`。
- 今日实时卡片：Redis `dashboard:realtime` 缓存 **300 秒**，口径是"支付成功订单"。
- 3 个接口：realtime（今日卡片）/ productRank（热销+滞销）/ categoryAnalysis（类目占比）；销售趋势与订单漏斗已按需求下线。
- **数字是自洽的**：类目占比之和 = 区间 GMV，漏斗逐层递减。

### 5. 三个规则型智能模块（强调"可解释、可配置"）
| 模块 | 算法 | 关键参数 |
|---|---|---|
| 库存预警 | 阈值规则（低/高水位）+ 顺带算补货量 | `ec_sys_config` 可改 |
| 销量预测 | 加权移动平均（近 7 天 0.5 / 8-30 天 0.3 / 31-90 天 0.2），新品走同类目兜底 | 权重配置化 |
| 智能客服 | 2-gram 余弦 + 包含度，取 max，阈值 0.85；答不上来转人工并沉淀知识 | 阈值可调 |
| 搜索 | 同义词组双向扩展（`ec_search_synonym`） | 词表可维护 |

**为什么不接大模型**：答辩场景要"可解释 + 可离线 + 零成本"，规则引擎的命中原因能直接展示给用户（"已按同义词扩展搜索"）。

## 四、高概率问题（按被问概率排序）

### A. 整体与选型
1. **为什么用 Spring Boot + Vue 前后端分离？** 职责清晰、可独立部署；前端只认 JSON 契约。
2. **为什么两个 Maven 模块而不是一个？** 原始骨架就是多模块，system 打可执行包、common 可复用；缺点是业务挤在 common 里，分层不彻底——承认，并说"如果重做会拆 api/service/dao 三层"。
3. **数据库为什么用 MyBatis-Plus？** 单表 CRUD 免写 SQL，复杂统计仍手写 SQL/注解，兼顾效率与可控。
4. **Redis 用在哪几处？** 登录态 `user:{id}`、看板实时缓存（5 分钟）、以及会话失效联动。
5. **MinIO 为什么不用本地磁盘？** 图片走对象存储，换机器/多实例不受影响；上传走后端 `/file/upload` 统一鉴权。

### B. 安全与权限
6. **JWT 无状态还需要 Redis？** JWT 只证明"签发过"，Redis 才代表"现在还有效"，支持强制下线和权限即时生效。
7. **怎么防越权（横向）？** 所有查询以 `SecurityUtils.getUserId()` 为准，不信任前端传的 userId；订单/地址/购物车按当前用户过滤。
8. **密码怎么存？** BCrypt 加盐哈希，接口返回与日志都脱敏（`@OperLog` 切面对密码字段打码）。
9. **SQL 注入？** 全部走 MyBatis 预编译参数 `#{}`，不拼接 `${}`。
10. **XSS？** Vue 默认转义，富文本场景没有；商品描述走纯文本。
11. **权限改了为什么要重新登录？** 菜单和路由是登录时一次性拉取缓存的——**这是已知短板**，可以说"改进方向是权限变更后主动清 Redis 登录态或推送刷新"。

### C. 交易与库存（重点区）
12. **怎么防超卖？** 见亮点 2：条件更新 + 影响行数判断，不用悲观锁也不用分布式锁。
13. **为什么加 version 字段？** 预留乐观锁；当前扣减用的是"条件更新"，等价且更轻，version 自增可用于排查并发。
14. **重复下单怎么办？** 唯一索引 `(user_id, idempotency_key)`，插入冲突即视为重复，直接返回已有订单。
15. **超时未支付怎么处理？** 每分钟定时扫描 `expire_time`，取消 + 回补库存 + 退券；**为什么不用延迟队列**——演示环境没有 MQ，扫描更简单可观测，生产可换 RocketMQ 延迟消息。
16. **取消订单库存没还怎么办？** 逐单独立事务 + 状态机保证幂等（已取消的单不会二次回补，因为状态校验在前）。
17. **订单里的商品改名了怎么办？** 明细表存的是**快照**（商品名/图/规格/单价），历史订单不受影响。
18. **退款流程？** 待发货可申请（1→5），管理员审核通过 5→6 并回补库存，驳回 5→1。
19. **金额用 double 吗？** 全部 `BigDecimal`/`decimal(12,2)`，避免浮点误差。

### D. 数据看板
20. **数据从哪来？** `ec_stat_daily`（日汇总）+ `ec_product_sales_daily`（商品日销）+ 行为埋点表。
21. **为什么不实时算？** 见亮点 4：760 天全量聚合 5 分钟，扛不住。
22. **缓存过期了会不会很慢？** 实时卡片只查当天，量小；趋势走汇总表，毫秒级。
23. **口径是什么？** 支付成功（status 1/2/3/5）且 `pay_time` 落在区间；退款单独看状态 6。
24. **漏斗怎么算？** 行为埋点 expose → click → cart，再对订单数，近 7 天。

### E. 智能模块
25. **客服答错了怎么办？** 阈值 0.85 才自动答，低于阈值转人工；人工补充的知识进知识库。
26. **2-gram 是什么？** 中文不分词，按相邻两字切分算余弦相似度，对错别字和语序不敏感；再叠加"知识问法被查询包含"的比例。
27. **预测准吗？** 加权移动平均只适合平稳销量；**大促和季节性会失真**——这是方法本身的局限，可换 Holt-Winters 或 LightGBM。
28. **预警阈值怎么定？** 全局默认在 `ec_sys_config`，商品可覆盖；触发后写 `ec_stock_alert`，首页有未处理条数提醒。

### F. 工程与部署
29. **怎么部署？** Nginx 托管前端静态资源 + 反代 `/api` 到 8888；后端 jar 常驻；MySQL/Redis/MinIO 独立。
30. **启动顺序？** MySQL/Redis/MinIO → 后端 8888 → 前端 8082（冷启动清单在 README）。
31. **有测试吗？** **没有自动化测试**，靠接口脚本 + 前端实测；诚实回答，并说"下一步补 JUnit + MockMvc 覆盖下单/取消/退款三条主链"。
32. **日志与排错？** `sys_oper_log` 记录写操作（谁、什么参数、耗时、成败），接口异常统一 `GlobalExceptionHandler`。

### G. 挑刺 / 压力题
33. **"这些商品和订单是脚本造的吧？"** 是，演示数据由 `sql/gen_bulk_data.py` 生成（seed 固定、可复现），但**业务链路是真跑的**：下单扣库存、状态流转、汇总表都由代码算出来，不是写死的假数据。
34. **并发量能到多少？** 单库单机、无缓存预扣，估算几十到上百 QPS；瓶颈在库存行锁和订单表写入，扩展方向是 Redis 预扣 + 分库。
35. **为什么不用微服务？** 课程规模下单体更划算：部署一个 jar，事务还是本地事务；拆开只会增加分布式事务成本。
36. **这个系统最大的问题是什么？** 三点：① 权限变更要重登；② 无自动化测试；③ 智能模块是规则不是模型。**主动说出来比被问出来好。**
37. **如果再做一个月，你先改什么？** 补测试 → 权限热更新 → 库存 Redis 预扣 → 预测换时序模型。
